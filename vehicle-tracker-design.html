1. Executive summary

Vehicles are fitted with third-party GPS tracker devices. Each device opens a TCP or UDP connection to our backend and periodically sends location reports in its vendor's protocol. The backend decodes every report into one normalised Position record, stores it, and pushes it in real time over WebSocket to every authenticated management client that is allowed to see that vehicle. The management application is a browser app: users sign in and watch their fleet move live on a map, with the map provider swappable.

Key decision: we will not write 200+ protocol decoders ourselves. The open-source Traccar server (Java, Apache 2.0) already ships decoders for 200+ protocols and 2,000+ device models. We embed it as a stateless Ingestion Gateway whose only job is bytes in → normalised Position out, published to Kafka. Everything downstream (business logic, storage, real-time push, auth, UI) is our own code and does not depend on Traccar internals.

3. The 200+ protocol problem

Tracker vendors each define their own wire format: binary (Teltonika Codec 8/8E, Concox/GT06, Queclink), ASCII (TK103, Meitrack, NMEA-like), HTTP-based (OsmAnd), and many variants of each. Every protocol has its own framing, login handshake, checksum, ACK rules, and set of extra attributes (fuel, CAN bus, temperature, RFID driver ID). Writing and maintaining 200 of these is years of work and requires physical test devices.

3.1 Options considered

OptionDescriptionProsCons
A. Write our own decodersNetty server + hand-written decoder per protocol.Full control, no external code.Years to reach 200 protocols; huge test burden. Not realistic.
B. Run Traccar as the whole productDeploy stock Traccar, customise its web UI.Fastest start; feature-rich.Monolith with its own data model, auth, UI; hard to scale horizontally or differentiate; we inherit its architecture.
C. Traccar as Ingestion Gateway RecommendedUse Traccar only for protocol decoding. Forward each decoded position to Kafka. Our own services do the rest.200+ protocols on day one; clean separation; our services scale independently; upgrades bring new protocols.Must manage the boundary carefully (version pinning, mapping its Position model to ours, command downlink path).

3.2 How the gateway works (option C)

  • Traccar runs one Netty pipeline per protocol, each listening on its own port (e.g. 5023 for GT06, 5027 for Teltonika). Devices are configured with our host and the port of their protocol.
  • When the protocol is unknown, a device can still be identified using Traccar's tooling against captured packets; ops then assign it to the right port.
  • The gateway runs stateless with respect to business data: device identity is checked against a cache fed from our Device Registry; it does not own users, vehicles or history.
  • Decoded positions are published to Kafka. Two integration paths, decided in a spike (see §15):
    1. Configuration-only: use Traccar's built-in position/event forwarding (it supports several forwarding targets, including message brokers, in recent versions — to be verified against the pinned version).
    2. Thin fork / extension: depend on Traccar's protocol module and add our own Netty handler at the end of the pipeline that maps Position → our Avro/Protobuf schema and produces to Kafka synchronously before the device is ACKed. This gives us the durability guarantee in §2.2.
  • Licence: Apache 2.0 allows commercial use and modification; we must keep the licence and NOTICE files and mark modified files.

4. High-level architecture

The design is event-driven around Kafka. The ingestion tier is deliberately thin and replaceable; Kafka decouples the bursty, connection-heavy device side from the client side. Every service is stateless and horizontally scalable; state lives in Kafka, PostgreSQL and Redis.

5. Component design

5.1 Ingestion Gateway (Traccar-based)

  • Responsibility: hold long-lived device connections, run protocol decoders, send protocol-level ACKs, publish normalised positions, deliver downlink commands to connected devices.
  • Device identity: the unique ID from the login/first packet is looked up in a local cache (Caffeine) loaded from the Device Registry (Core API) and kept in sync via the device.registry Kafka topic. Unknown IDs are published to device.unknown for ops review instead of being silently dropped.
  • Session ownership: on connect, the gateway writes deviceId → podId to Redis (TTL refreshed on traffic) so command delivery can be routed to the right pod.
  • Durability: Kafka producer with acks=all, idempotence on; device ACK is sent only after the produce completes. If Kafka is unreachable, the gateway stops ACKing and devices buffer locally (most trackers store hundreds to thousands of points).
  • Scaling: N identical pods behind a Layer-4 load balancer. TCP connections are sticky by nature; UDP protocols need source-IP affinity.

5.2 Position Processor

  • Kafka Streams (or Spring Kafka consumers) reading positions.raw, partitioned by deviceId so each device's points are processed in order.
  • Validate: drop invalid fixes (lat/lon 0,0, no GPS fix, future timestamps), flag outliers (impossible jumps by speed).
  • Dedupe: devices resend buffered points after reconnecting; dedupe by (deviceId, fixTime).
  • Enrich: attach vehicleId, tenantId, groupIds; compute derived fields (odometer delta, moving/stopped state).
  • Events (v1): online/offline, ignition on/off, overspeed, geofence enter/exit (PostGIS geometries cached in memory), alarms from device attributes. Output to events.
  • Writes positions.enriched; late/historical points (buffered offline data) are marked historical=true so the live map does not jump back in time.

5.3 History Writer

  • Consumes positions.enriched and events, writes in batches (e.g. 500 rows / 200 ms) to TimescaleDB using COPY or batched inserts.
  • Idempotent upserts on (device_id, fix_time) so reprocessing is safe.

5.4 Live Hub (WebSocket service)

  • Spring Boot with Spring WebSocket (STOMP over WebSocket, or raw WebSocket with a small JSON protocol — see §7). Reactive (WebFlux/Netty) for high connection counts.
  • Each pod consumes positions.enriched and events with its own consumer group (broadcast) and forwards only to its locally connected sessions whose authorisation scope includes the vehicle. Alternative at larger scale: a router publishes to Redis channels per tenant and pods subscribe only to tenants they hold sessions for.
  • Snapshot on connect: on subscribe, the client receives the last known position of every visible vehicle from Redis, then incremental updates.
  • Back-pressure: per-session bounded queue; if a slow client falls behind, older updates for the same vehicle are coalesced (only the latest matters for a live map).
  • Optional viewport filtering: clients may send their map bounds; the hub only sends vehicles inside the box (+ margin). Important for tenants with tens of thousands of vehicles.

5.5 Core API

  • Spring Boot 4 REST service (Spring MVC, Spring Security as OAuth2 Resource Server).
  • Owns tenants, users (profile; credentials live in the IdP), roles, groups, vehicles, devices (Device Registry), geofences, history queries, command requests, audit log.
  • Publishes registry changes to device.registry for gateway caches; publishes command requests to device.commands.

5.6 Identity Provider

  • Keycloak (or a managed OIDC provider: Auth0, Entra ID, Cognito). Supports SSO for enterprise customers, MFA, password policy.
  • Access token (JWT, ~5 min) carries sub, tenant_id, roles. Fine-grained group access is resolved by Core API / Live Hub and cached.

6. Data flow

6.1 Uplink: device report → live map

#StepComponent
1Device connects to track.example.com:5027 and sends login + location packet.Device → L4 LB
2Protocol decoder frames and decodes packet; unique ID resolved against the registry cache.Ingestion Gateway
3Normalised Position produced to positions.raw (key = deviceId, acks=all).Gateway → Kafka
4Protocol ACK returned to device.Gateway → Device
5Validate, dedupe, enrich with vehicle/tenant; derive events; produce to positions.enriched.Position Processor
6aBatch-written to TimescaleDB.History Writer
6bLast-known position updated in Redis; pushed to authorised WebSocket sessions.Live Hub
7Browser moves marker (with smooth interpolation), updates side panel.Web App

6.2 Downlink: user command → device (v2)

  1. User clicks “Request position” / “Immobilise” → POST /api/v1/devices/{id}/commands (permission check, audit log, optional 2-step confirmation for dangerous commands).
  2. Core API writes the command (status PENDING) and produces to device.commands.
  3. The gateway pod that owns the session (looked up in Redis, or all pods filter by deviceId) encodes it in the device's protocol and sends it. If the device is offline, the command is queued until it reconnects (or expires).
  4. Device response → device.status → Core API updates status → Live Hub notifies the user.

7. Real-time WebSocket contract

Endpoint: wss://app.example.com/ws/live. The access token is sent in the first message (not in the URL, to keep it out of logs). The server closes the socket when the token expires unless a refreshed token is sent.

{ "type": "auth", "token": "<JWT>" }
{ "type": "subscribe", "scope": { "groups": ["g-12"], "vehicles": [] },
  "bounds": { "n": 51.70, "s": 51.28, "e": 0.33, "w": -0.51 } }   // bounds optional
{ "type": "bounds", "n": 51.6, "s": 51.4, "e": 0.1, "w": -0.3 }
{ "type": "ping" }

// server → client

  "vehicleId": "v-8812", "deviceId": "d-3391",
  "fixTime": "2026-11-06T18:27:04Z", "serverTime": "2026-11-06T18:27:05.112Z",
  "lat": 51.50735, "lon": -0.12776, "speedKph": 42.5, "course": 118,

9.2 Time-series (TimescaleDB hypertable)

position (
  device_id   uuid        not null,
  vehicle_id  uuid,
  tenant_id   uuid        not null,
  fix_time    timestamptz not null,
  server_time timestamptz not null,
  lat double precision, lon double precision,
  speed_kph real, course smallint, altitude real, satellites smallint,
  valid boolean, ignition boolean,
  attributes  jsonb,
  primary key (device_id, fix_time)
)  -- hypertable on fix_time, 1-day chunks; compression after 7 days;
   -- retention policy per tenant; continuous aggregate for 1-minute downsampling.

Volume estimate: 10,000 vehicles × one point every 10 s while moving (~10 h/day) ≈ 36 M rows/day. At ~150 bytes/row uncompressed ≈ 5.4 GB/day; TimescaleDB compression typically cuts this by an order of magnitude. At 100k vehicles, consider a dedicated time-series cluster or ClickHouse for history.

10. Management web application

10.1 Stack

  • React + TypeScript, Vite build, served as static assets from CDN / object storage.
  • Auth: OIDC Authorization Code + PKCE (e.g. oidc-client-ts); tokens in memory, silent refresh.
  • State: TanStack Query for REST data; a dedicated live store (Zustand) fed by the WebSocket client.
  • UI components: a mature component library (e.g. MUI or Mantine) for admin screens.

10.2 “Any map” — map abstraction

The UI talks to a small MapAdapter interface, not to a vendor SDK directly:

interface MapAdapter {
  mount(el: HTMLElement, opts: { center: LatLng; zoom: number }): void;
  upsertMarker(id: string, p: LatLng, style: MarkerStyle): void;
  removeMarker(id: string): void;
  drawTrack(id: string, points: LatLng[], style: LineStyle): void;
  fitBounds(b: Bounds): void;
  onBoundsChange(cb: (b: Bounds) => void): void;
  destroy(): void;
}
  • Default adapter: MapLibre GL JS (open source, WebGL, handles thousands of markers via GeoJSON sources/clustering). With raster/vector tile sources it covers OpenStreetMap, MapTiler, Mapbox styles, Esri, HERE tiles, etc.
  • Additional adapters for providers that require their own SDK: Google Maps JS API, optionally Leaflet for lightweight/legacy needs.
  • Provider choice: tenant default + user preference; API keys per tenant are stored server-side and delivered via /me.
  • Marker animation: interpolate between consecutive positions over the reporting interval so movement looks smooth; rotate icon by course.

11. Security

AreaMeasures
User accessOIDC; short-lived JWT; refresh via IdP; MFA for admins; RBAC (Viewer, Dispatcher, Admin, Super-admin).
Tenant isolationEvery row carries tenant_id; enforced in the repository layer and optionally PostgreSQL Row-Level Security; Live Hub filters on server side — never trusts client scope.
Device channelMost GPS protocols are unauthenticated plaintext. Mitigations: only registered unique IDs accepted; anomaly detection (same IMEI from two IPs, impossible jumps); TLS ports for devices that support it; private APN / VPN with mobile operator for high-security customers.
TransportTLS 1.2+ for all web/API/WebSocket traffic; WebSocket origin check; token in first message, not URL.
CommandsDangerous commands (immobiliser) need ADMIN role, confirmation, and are fully audited.
AbusePer-IP connection limits at the gateway; API rate limits; WAF in front of web endpoints.
PrivacyLocation data is personal data under UK/EU GDPR when linked to drivers: retention limits, data export/erasure per tenant, optional “private mode” for off-duty hours.

13. Deployment & operations

  • Packaging: one Docker image per service; Kubernetes (EKS/GKE/AKS or self-managed) with Helm charts. Local dev via Docker Compose (Kafka, Postgres/Timescale, Redis, Keycloak).
  • Gateway networking: needs hundreds of ports open. Use a cloud Network Load Balancer with a port range (or a dedicated node pool with hostNetwork + external L4 balancer such as HAProxy). Only enable ports for protocols actually in use to reduce attack surface.
  • Managed options: managed Kafka (MSK, Confluent, Aiven), managed Postgres with TimescaleDB (Timescale Cloud) and managed Redis reduce ops load.
  • Observability: Micrometer → Prometheus/Grafana; OpenTelemetry tracing across services (trace id stamped at the gateway); structured JSON logs → Loki/ELK. Key metrics: connected devices per protocol, decode errors per protocol, ingest lag, Kafka consumer lag, end-to-end latency, WebSocket sessions.
  • Raw packet capture: optional per-device hex logging (time-limited) for troubleshooting new device models.
  • CI/CD: GitHub Actions → build, test, container scan → deploy to staging → production with canary for gateway (device connections drain gracefully).
  • Testing: device simulators replaying recorded packets per protocol; load tests (Gatling/k6) for 100k simulated connections and WebSocket clients.
